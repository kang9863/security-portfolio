# AI/MCP 기반 버그헌팅 워크플로우 정리

> 이 문서는 HexStrike AI, MCP, Cursor, Codex 같은 LLM 기반 도구를 보안 학습과 보고서 작성에 어떻게 안전하게 붙일 수 있는지 정리한 학습 보고서입니다. 실제 서비스가 아니라 허가된 랩, CTF, 본인 자산 범위에서만 사용하는 것을 기준으로 작성했습니다.

## 1. 작성 목적

헌팅마스터 B트랙에는 웹/모바일 취약점 분석뿐 아니라 AI를 활용한 버그헌팅 흐름도 포함되어 있습니다. 그래서 단순히 “AI가 취약점을 찾아준다”는 관점이 아니라, LLM이 어떤 작업을 보조할 수 있고 어디서 사람의 판단이 반드시 필요한지 정리했습니다.

제가 정리한 핵심은 다음과 같습니다.

- LLM은 정찰 결과 요약, 체크리스트 생성, 보고서 초안 정리처럼 반복적인 분석 보조에 강하다.
- MCP는 LLM과 외부 도구 사이를 연결하는 인터페이스 역할을 한다.
- HexStrike 같은 도구는 Nmap, Nuclei, Gobuster, OSINT 도구의 실행 계층으로 볼 수 있다.
- 하지만 버그헌팅에서는 허가 범위, 로그 관리, 마스킹, 수동 검증이 자동화보다 더 중요하다.

## 2. 전체 구조

조사한 구조는 다음 흐름으로 이해했습니다.

```text
사용자 프롬프트
-> LLM 클라이언트(Codex / Cursor / Gemini 등)
-> MCP 연결
-> HexStrike 또는 MCP 서버
-> 보안 도구 실행(Nmap / Nuclei / Gobuster / OSINT 도구 등)
-> 결과 수집
-> LLM이 요약, 분류, 다음 확인 항목 제안
-> 사람이 재현 가능성과 영향도를 검증
```

여기서 중요한 점은 LLM이 최종 판단자가 아니라는 것입니다. LLM은 결과를 정리하고 다음 확인 항목을 제안할 수 있지만, 실제 취약점 여부와 영향도는 사람이 직접 재현해서 확인해야 합니다.

## 3. MCP를 붙일 때 생각한 기준

MCP 서버를 붙이면 LLM이 파일, 도구, 명령 실행 환경과 연결될 수 있습니다. 편리하지만 동시에 위험해질 수 있기 때문에 다음 기준을 먼저 세워야 한다고 정리했습니다.

| 기준 | 정리한 내용 |
|---|---|
| 스코프 제한 | CTF, 실습 랩, 본인 자산, 명시적으로 허가된 대상만 사용 |
| 명령 승인 | 스캔, 쓰기, 삭제, 익스플로잇성 명령은 사람이 한 번 더 확인 |
| 로그 관리 | 실행한 명령, 대상, 결과를 기록하되 공개 전 민감 값 제거 |
| 마스킹 | API key, token, cookie, password, hash, flag, 개인정보는 공개 금지 |
| 재현성 | AI 요약만 믿지 않고 원본 요청/응답, 도구 출력, 수동 검증 결과를 남김 |
| 모드 분리 | 조사/정리 모드와 실제 실행 모드를 구분 |

## 4. 버그헌팅에서의 사용 흐름

제가 포트폴리오용으로 정리한 사용 흐름은 공격 자동화가 아니라 “분석 보조 루프”입니다.

### 4.1 범위 확인

먼저 대상이 허가된 랩인지 확인합니다. 실제 서비스라면 프로그램 정책, 허용된 도메인, 금지 행위, rate limit, 테스트 계정 사용 가능 여부를 먼저 봐야 합니다.

```text
대상 확인
-> 허가 범위 확인
-> 금지 행위 확인
-> 테스트 강도 결정
-> 로그 저장 방식 결정
```

### 4.2 정찰 결과 정리

Nmap, Gobuster, Nuclei 같은 도구 출력은 길고 반복되는 정보가 많습니다. 이 단계에서 LLM을 사용하면 포트, 서비스, 웹 경로, 기술 스택, 의심 지점을 표로 묶는 데 도움이 됩니다.

예시로는 다음처럼 쓰는 흐름을 생각했습니다.

```text
원본 스캔 결과
-> 서비스별 분류
-> 웹 엔드포인트 후보 정리
-> 인증 필요 여부 구분
-> 다음 수동 확인 항목 제안
```

단, 이때도 LLM이 만든 결론은 그대로 보고서에 넣지 않고 원본 결과와 비교합니다.

### 4.3 웹 취약점 확인 보조

웹 취약점 분석에서는 LLM에게 페이로드를 무작정 만들게 하는 것보다, 요청이 어떤 문맥에서 처리되는지 설명하게 하는 쪽이 더 안전하다고 봤습니다.

확인 항목:

- 입력값이 query, form, JSON, cookie, header 중 어디서 들어오는지
- 서버에서 SQL, HTML, JavaScript, file path, template 중 어떤 문맥으로 해석되는지
- 인증/권한 검사가 요청 전후 어느 위치에서 이뤄지는지
- 오류 메시지나 응답 차이가 실제 취약점 근거인지 단순 동작 차이인지

이 흐름은 제가 SQL Injection, XSS, 로그인 로직 분석 보고서에서 쓰는 방식과 연결됩니다.

### 4.4 OSINT self-audit

노트에서는 이메일이나 사용자명을 시작점으로 공개 정보를 연결하는 OSINT self-audit도 정리했습니다. 다만 개인정보를 다루기 때문에 공개 포트폴리오에는 실제 식별 정보를 넣지 않는 것을 원칙으로 잡았습니다.

OSINT self-audit 루프:

```text
식별자 정규화
-> 공개 프로필 확인
-> 저장소와 작성자 페이지 확인
-> 여러 출처의 신호 교차 검증
-> Low / Medium / High 신뢰도 분류
-> 내부용 전체 보고서와 공개용 마스킹 보고서 분리
```

이 부분에서 배운 점은 OSINT가 단순히 많이 찾는 문제가 아니라, 잘못된 연결을 줄이고 민감 정보를 안전하게 다루는 문제라는 것입니다.

## 5. Human-in-the-Loop 운영 원칙

AI 보조 워크플로우를 쓸 때 가장 중요한 부분은 사람이 중간에서 멈추고 확인하는 지점입니다.

제가 기준으로 잡은 중단 지점은 다음과 같습니다.

- 허가 범위가 애매한 대상이 입력된 경우
- 스캔 강도가 높아질 수 있는 경우
- 계정 잠금, 서비스 장애, 과도한 요청이 발생할 수 있는 경우
- 인증 정보, 세션, 토큰, 개인정보가 결과에 포함된 경우
- LLM이 취약점이라고 판단했지만 수동 재현 근거가 없는 경우
- 외부 공개 보고서에 넣기 전 마스킹이 필요한 경우

이 기준을 두면 AI를 쓰더라도 결과물이 “자동으로 돌린 흔적”이 아니라, 사람이 범위와 근거를 통제한 분석 기록으로 남습니다.

## 6. AI에게 맡길 수 있는 일과 맡기면 안 되는 일

AI/MCP를 보안 학습에 붙일 때 역할을 명확히 나눠야 한다고 정리했습니다.

| 구분 | 허용할 수 있는 사용 |
| --- | --- |
| 정리 | 긴 Nmap/Nuclei/Gobuster 결과를 서비스별 표로 요약 |
| 체크리스트 | SQLi, XSS, IDOR, 모바일 분석 확인 항목 생성 |
| 보고서 초안 | 재현 절차, 영향도, 대응 방안의 문장 정리 |
| 비교 | 정상 요청과 취약 요청의 차이점 요약 |
| 마스킹 보조 | 공개하면 안 되는 값 후보 표시 |

반대로 아래 작업은 AI가 단독으로 결정하면 안 된다고 봤습니다.

| 구분 | 이유 |
| --- | --- |
| 허가되지 않은 대상 스캔 | 스코프 위반 가능성 |
| 높은 강도의 자동 스캔 | 서비스 장애 또는 rate limit 위반 가능성 |
| 익스플로잇 실행 | 영향 범위를 사람이 통제해야 함 |
| 계정 잠금 가능 테스트 | 실제 사용자/서비스에 피해 가능성 |
| 개인정보 OSINT 결론 | 오탐과 사생활 침해 위험 |
| 보고서 최종 판단 | 재현성과 영향도는 사람이 검증해야 함 |

## 7. 검증 루프 예시

AI가 제안한 내용을 그대로 믿지 않고 다음 루프로 확인합니다.

```text
AI 요약 확인
-> 원본 도구 출력과 대조
-> 수동 요청 또는 명령으로 재현
-> 취약점 조건과 영향도 분리
-> 공개 가능한 증거만 남김
-> 보고서 문장을 직접 다듬음
```

예를 들어 Nuclei가 취약점 후보를 표시했다면, 바로 보고서에 넣지 않고 해당 HTTP 요청을 직접 보내 응답을 확인합니다. XSS 후보라면 실제 브라우저 문맥에서 실행되는지 확인하고, IDOR 후보라면 계정 전환 검증을 해야 합니다.

## 8. 공개 보고서 작성 기준

포트폴리오에 공개할 때는 다음 기준을 적용합니다.

| 항목 | 공개 기준 |
|---|---|
| 도구 이름 | 공개 가능 |
| 명령 전체 | 실습 랩 기준이면 공개 가능, 실제 대상 정보는 치환 |
| IP / 도메인 | CTF/랩은 공개 가능, 실제 서비스는 마스킹 |
| 토큰 / 쿠키 / 세션 | 공개 금지 |
| 비밀번호 / 해시 / 플래그 | 공개 금지 또는 일부 마스킹 |
| 개인정보 | 공개 금지 |
| AI가 작성한 초안 | 원본 근거 확인 후 내 문장으로 재작성 |

특히 OSINT나 버그바운티 보고서에서는 내부용 보고서와 공개용 포트폴리오 문서를 분리해야 한다고 정리했습니다.

## 9. 포트폴리오와 연결되는 지점

이 보고서는 제 포트폴리오의 다른 문서들과 다음처럼 연결됩니다.

- SQL Injection / XSS 보고서: LLM을 페이로드 생성보다 입력 문맥 정리에 활용
- 로그인 로직 분석: 인증/인가 흐름을 표로 분리하고 누락 지점을 검토
- HTB / THM 라이트업: 긴 도구 출력과 공격 경로를 단계별 복기로 정리
- Nessus / IDS 보고서: 스캔 결과와 탐지 룰을 비교해 검증 흐름 정리
- 모바일 분석 보고서: jadx-gui, Frida, logcat 결과를 공개 가능한 증거와 비공개 값으로 분리

## 10. 앞으로 보강할 점

현재 문서는 조사와 운영 기준 중심입니다. 앞으로 실제 허가된 랩에서 AI/MCP를 사용할 경우에는 다음 내용을 추가할 계획입니다.

- 실행 전 스코프 확인 기록
- 도구별 원본 출력과 AI 요약 비교
- AI가 잘못 해석한 사례와 수정 내용
- 마스킹 전/후 공개 기준
- 수동 재현으로 확정한 취약점과 탈락한 후보 구분

이렇게 보강하면 단순한 AI 도구 소개가 아니라, AI를 사용하더라도 보안 분석의 책임과 검증을 사람이 가져간다는 점을 더 명확히 보여줄 수 있습니다.

## 11. 배운 점

AI 기반 보안 도구는 결과를 빠르게 정리하고 다음 확인 항목을 제안하는 데 도움이 됩니다. 하지만 버그헌팅에서 중요한 것은 “AI가 무엇을 실행했는가”보다 “사람이 어떤 범위를 허가했고, 어떤 근거로 취약점이라고 판단했으며, 공개 가능한 증거만 남겼는가”라고 느꼈습니다.

앞으로 AI/MCP 워크플로우를 사용할 때도 자동 실행보다 범위 제한, 재현성, 마스킹, 보고서 품질을 먼저 기준으로 삼을 계획입니다.
