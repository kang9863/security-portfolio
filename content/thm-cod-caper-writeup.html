THM The Cod Caper 분석 - SQLi SSH와 로컬 바이너리

1. 개요

The Cod Caper는 웹 취약점, 리눅스 내부 정찰, 기초 BOF가 하나의 흐름으로 이어지는 TryHackMe 실습이다. 단일 취약점 하나만 보는 문제가 아니라, 웹 로그인 폼에서 시작해 서버 내부 접근과 로컬 권한 상승까지 연결해야 했다.

전체 흐름은 다음과 같이 정리할 수 있다.

관리자 로그인 페이지 발견
-> SQL Injection 가능성 확인
-> sqlmap으로 DB 구조와 계정 정보 확인
-> SSH 접속 및 키/권한 확인
-> 숨겨진 pass 파일 탐색
-> root 권한으로 실행되는 BOF 바이너리 분석
-> RET 주소를 기존 shell 함수로 덮어쓰기
-> 해시/비밀번호 복구로 결과 확인

이 라이트업은 플래그 자체보다 “어떤 단서를 보고 다음 단계로 넘어갔는지”를 설명하는 데 초점을 맞췄다. 모든 실습은 허가된 THM 랩 환경에서 진행했다.

2. 대상 / 환경

항목 내용
플랫폼 TryHackMe 실습 랩
주요 영역 Web, Linux Enumeration, BOF
사용 도구 브라우저, Burp/HTTP 확인, sqlmap, SSH, GDB, readelf, Python, John

3. 초기 웹 진입점

웹 디렉터리 정찰 과정에서 관리자 로그인 페이지를 확인했다. 여기서 중요한 점은 “로그인 페이지가 있다”가 아니라, 로그인 요청이 SQLi를 검증할 수 있는 명확한 입력 지점이라는 것이다.

먼저 작은따옴표와 기본적인 로그인 우회 payload로 응답 차이를 확인했다. 입력값에 따라 서버 응답이 달라지는 것을 보고 SQLi 가능성이 있다고 판단했고, 이후에는 sqlmap으로 구조화된 추출을 진행했다.

4. SQL Injection 검증 및 DB 추출

로그인 요청은 POST 방식으로 username, password 값을 전달했다. 수동 확인 후 sqlmap으로 대상 URL과 form body를 지정해 DB 구조를 확인했다.

sqlmap -u http://<LAB_IP>/administrator.php --forms
sqlmap -u http://<LAB_IP>/administrator.php --data "username=&password=" --dbs
sqlmap -u http://<LAB_IP>/administrator.php --data "username=&password=" -D users --tables
sqlmap -u http://<LAB_IP>/administrator.php --data "username=&password=" -D users -T users --dump

DB enumeration 결과를 통해 백엔드 쿼리가 injectable하고, 애플리케이션 DB에서 사용자 정보를 추출할 수 있음을 확인했다.

이 단계에서 정리한 재사용 가능한 루틴은 다음과 같다.

폼 발견
-> 요청 방식과 파라미터 확인
-> 최소 payload로 수동 테스트
-> 성공/실패 응답 차이 비교
-> 요청 구조를 이해한 뒤 sqlmap으로 보조 검증

5. SSH 접근 및 내부 파일 탐색

웹 취약점으로 확보한 계정 정보가 SSH에도 재사용되는지 확인했다. SSH 키를 사용할 수 있는 경우에는 권한이 너무 넓게 설정되어 있지 않은지, 실제로 해당 키로 접속 가능한지 확인해야 한다.

서버 내부에 들어간 뒤에는 로컬 정찰을 진행했다. 일반적인 사용자 경로에 보이지 않는 pass 파일이 있었기 때문에 파일시스템을 직접 검색했다.

find / -name pass 2>/dev/null

6. BOF 후보 바이너리 분석

권한 상승 경로는 표준 입력의 영향을 받는 바이너리에서 시작됐다. 취약 함수는 고정 크기의 stack buffer를 사용하면서 입력 길이를 안전하게 제한하지 않았다.

분석에서 가장 먼저 답해야 할 질문은 이것이었다.

사용자 입력이 RET 주소에 도달하려면 몇 바이트가 필요한가?

32-bit 구조에서 확인한 레이아웃은 다음과 같았다.

buffer: 40 bytes
saved frame pointer: 4 bytes
RET overwrite 시작 위치: 44 bytes 이후

재현 시 충분히 긴 입력과 레지스터 값을 이용해 RET 오프셋을 별도로 측정해야 한다. 현재 다음 캡처는 disassembly이며, 실제 크래시·cyclic 오프셋 검증의 증거와 구분한다.

7. RET overwrite 전략

RET 오프셋이 별도 검증되면 바이너리 안에 이미 존재하는 유용한 함수를 후속 대상으로 검토한다. 이 문제에서는 shell 관련 동작을 수행하는 함수가 있었기 때문에 shellcode를 직접 주입하기보다, RET를 해당 함수 주소로 덮어쓰는 방식이 더 단순했다.

payload 구조는 다음과 같다.

"A" * 44 + target_function_address

예시 구조:

python -c 'print "A"*44 + "\xcb\x84\x04\x08"' | ./root

함수 주소는 랩 인스턴스나 바이너리 빌드 상태에 따라 달라질 수 있으므로, 재현할 때는 readelf, objdump, GDB로 다시 확인해야 한다.

8. 결과 확인

보유한 계정 분석 자료에는 John으로 비밀번호를 복원한 결과가 남아 있다. 이 결과는 BOF 크래시·오프셋 검증 및 전체 체인 완료와 분리해 기록한다.

이 문제의 핵심은 취약점 하나를 크게 과장하는 것이 아니라, 작은 단서들이 어떻게 다음 단계로 이어지는지 설명하는 것이다.

  • 웹 로그인 입력이 SQL 문법으로 해석됐다.
  • DB 데이터가 서버 계정 접근으로 이어졌다.
  • 로컬 정찰에서 권한 상승 후보 바이너리를 찾았다.
  • C 소스와 GDB disassembly를 확인하고 제어 흐름 변조의 후속 검증 항목을 정리했다.

9. 영향도

실제 환경이라면 웹 로그인 취약점이 서버 내부 접근과 권한 상승으로 이어지는 고위험 체인이다. 전체 체인이 성공하면 민감 파일, 계정 정보, 서버 관리자 권한까지 노출될 수 있다.

구분 영향
웹 SQLi로 DB 사용자 정보 추출 가능
계정 웹 계정과 OS 계정 재사용 시 SSH 접근 가능
서버 내부 숨겨진 파일, 권한 상승 바이너리 노출
권한 상승 BOF를 이용해 root 권한 동작 호출 가능
최종 영향 서버 장악, 민감정보 탈취, 추가 내부 이동 가능

10. 대응 방안

  • 인증 쿼리는 Prepared Statement로 작성한다.
  • 웹 애플리케이션 DB에 재사용 가능한 OS 계정을 저장하지 않는다.
  • 웹 계정과 시스템 계정의 비밀번호를 분리한다.
  • SSH private key는 노출 경로에 두지 않고 권한을 엄격히 제한한다.
  • SUID/root helper 바이너리는 꼭 필요한 경우에만 둔다.
  • 입력 함수는 길이 제한이 있는 안전한 함수로 교체한다.
  • Canary, PIE, NX, Full RELRO 같은 보호 기법을 적용한다.

11. 학습한 점

이 실습은 웹 해킹과 시스템 해킹을 따로 보지 않고 하나의 공격 경로로 연결해보는 데 의미가 있었다. 포트폴리오에서 보여주고 싶은 핵심은 다음 흐름이다.

HTTP 요청 분석 -> SQLi 검증 -> 계정 재사용 확인 -> 로컬 정찰 -> 바이너리 분석 -> exploit 작성

각 단계는 앞 단계의 결과를 근거로 진행되어야 한다. 캡처도 단순 인증샷이 아니라, “왜 다음 단계로 넘어갈 수 있었는지”를 증명하는 자료로 배치하는 것이 중요하다고 느꼈다.
