AI 도구의 실행 상태와 증거 관리

AI가 제안한 작업, 도구가 실제 수행한 작업과 최종 판단의 근거를 구분하기 위한 구성 기록이다. Multi-LLM/MCP 통합 문서에서 기능별 서버 선택, 실행 승인, 결과 정규화와 반복 실패 처리를 정리한 내용을 연결했다.

1. 계획과 실행을 구분

계획에 web-probe 같은 분류가 있다고 해서 해당 도구가 실제 실행됐다는 뜻은 아니다. 서버 선택, 도구와 인자 확인, 승인, 실행·결과 수집을 별도 단계로 설명해야 한다. 범위 메타데이터도 도구 호출 시의 검사를 대신하지 않는다.

2. 결과 상태를 나누는 기준

상태 최종 분석에서 다룰 내용
성공 원본 출력과 기대 조건을 대조
부분 성공 확보된 자료와 실패한 부분을 따로 기록
실패 실패 지점과 오류 메시지 확인
결과 불명 중단 뒤 실행 여부·부작용을 확인하고 재실행 판단

부분 성공을 완전한 성공으로 합치거나, 응답이 없었다는 이유만으로 안전하게 재실행할 수 있다고 판단하지 않는다. 반복 실패는 Circuit Breaker와 연결해 같은 호출이 계속 이어지는 조건을 점검한다.

3. 증거를 결과와 연결

작업·도구·입력 조건
  → 실행 상태
  → 원본 로그 또는 산출물 경로
  → SHA-256 등 파일 식별 정보
  → 검토한 사실과 남은 확인 항목

경로와 해시는 결과가 어느 파일에 근거하는지 연결하는 식별 정보다. 해시가 있다고 해서 취약점 판단이나 로그의 모든 내용이 참이라는 뜻은 아니다. 원본 요청·응답 및 실행 조건을 함께 설명해야 한다.

4. 외부 검토와 정보 전달

외부 모델 검토에는 제공자 선택과 전송 본문 확인이 필요하다. 통합 문서에는 승인 UI 문구와 실제 검토 패킷의 내용이 다를 수 있는 지점도 정리돼 있다. UI 설명만으로 전송 범위를 판단하지 않고 실제 구성과 본문을 대조하는 관점이다.

5. 기능 이름과 실제 구현 범위

이름·모듈 현재 자료의 의미
resume 저장된 계획 표시; 중단한 도구의 자동 재실행과 구분
Notion Bridge 구성 골격; 모든 결과의 자동 저장 완료와 구분
Token Tracker 모듈 존재; 전체 작업의 비용 자동 집계와 구분
참고 도구 카탈로그 참고 항목; 설치·통합·운영 완료 수와 구분

6. 보안 분석에 적용한 방식

Juice Shop에서 MCP 연결 확인과 별도 SQLi 검증을 다른 실행으로 남긴 것도 같은 기준이다. AI 요약, 도구의 관찰과 수동·원본 검증 결과를 나눠 보고서의 결론이 근거보다 커지지 않도록 정리한다. 현재 서버 연결과 런타임 테스트는 이 문서 작성 과정에서 새로 측정하지 않았다.
