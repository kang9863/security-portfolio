HTB Spookifier 라이트업 - SSTI (Mako Template)

1. 개요

Hack The Box Web Challenge Spookifier는 사용자가 입력한 이름을 여러 형태의 spooky font로 변환해 보여주는 웹 애플리케이션이다. 입력값이 서버 측 템플릿에 안전하지 않게 삽입되어 Server-Side Template Injection(SSTI)이 발생한다.

초기 로드맵에는 Jinja2 기반 SSTI로 적어두었지만, Spookifier는 Flask 애플리케이션에서 Mako 템플릿을 사용하는 케이스로 정리하는 것이 정확하다. 이 보고서는 템플릿 엔진 식별, 입력 반영 위치 확인, Mako 문법 기반 SSTI 검증, 파일 읽기 영향도까지의 흐름을 정리한다.

  • 사용자 입력이 서버 측 템플릿에 삽입되는 지점을 식별한다.
  • Jinja2와 Mako의 SSTI 문법 차이를 구분한다.

  • 개발 관점의 대응 방안을 정리한다.

4. 정찰 및 입력 지점 확인

애플리케이션은 이름 입력 폼을 제공하고, 제출된 값을 여러 글꼴 형태로 변환해 화면에 출력한다.

GET /?text=guest

입력값이 응답 HTML에 반영되므로 먼저 다음 항목을 확인한다.

점검 항목 확인 관점
반영 위치 입력값이 HTML 본문, 속성, 템플릿 결과 중 어디에 나타나는가
처리 위치 클라이언트 JavaScript 처리인지, 서버 렌더링인지
특수문자 처리 <, >, {, }, $ 같은 문자가 보존되는가
템플릿 흔적 Flask, Werkzeug, Mako, Jinja2 같은 프레임워크/엔진 단서

5. 취약 코드 흐름

Spookifier의 핵심 문제는 변환된 문자열을 안전한 데이터로 다루지 않고, 문자열 포맷팅 후 다시 템플릿으로 렌더링하는 구조다.

def generate_render(converted_fonts):
    result = """
        <tr>
            <td>{0}</td>
        </tr>
        <tr>
            <td>{1}</td>
        </tr>
        <tr>
            <td>{2}</td>
        </tr>
        <tr>
            <td>{3}</td>
        </tr>
    """.format(*converted_fonts)

    return Template(result).render()

문제의 핵심은 converted_fonts 안에 사용자 입력이 포함되고, 그 결과 문자열이 Mako Template()에 다시 전달된다는 점이다. 이 경우 입력값이 단순 텍스트가 아니라 템플릿 문법으로 해석될 수 있다.

6. SSTI 검증

6.1 Jinja2 문법과 Mako 문법 구분

Jinja2에서는 보통 다음과 같은 payload로 산술 표현식 실행 여부를 확인한다.

{{ 7 * 7 }}

하지만 Spookifier는 Mako 기반이므로 ${...} 문법을 사용한다.

${7*7}

응답에 49가 포함되면 입력값이 서버 측 템플릿 표현식으로 평가된 것이다.

6.2 Mako 표현식 실행 확인

GET /?text=${7*7}

예상 결과:

49

이 단계에서 XSS와 SSTI를 구분할 수 있다. XSS는 피해자 브라우저에서 JavaScript가 실행되는 문제이고, SSTI는 서버가 템플릿 표현식을 해석해 결과를 응답에 포함하는 문제다.

7. 영향도 검증

Mako 템플릿에서 Python 객체 접근이 가능하면 서버 파일 읽기 또는 명령 실행으로 이어질 수 있다. CTF 환경에서는 보통 /flag.txt 또는 애플리케이션 상위 경로의 flag 파일을 대상으로 영향도를 확인한다.

${open('/flag.txt').read()}

환경에 따라 직접 open() 접근이 제한되거나 출력 위치가 깨질 수 있으므로, 객체 접근 체인을 통해 os 모듈에 접근하는 방식도 사용된다.

${self.module.cache.util.os.popen('id').read()}
${self.module.cache.util.os.popen('cat /flag.txt').read()}

제출용 포트폴리오에는 실제 flag 값과 동적 인스턴스 주소를 포함하지 않는다. 대신 파일 읽기 가능성, 서버 명령 실행 가능성, 영향 범위를 중심으로 기록한다.

10. 대응 방안

10.1 사용자 입력을 템플릿으로 재렌더링하지 않기

사용자 입력은 템플릿 문법이 아니라 데이터로만 전달해야 한다.

return render_template("index.html", converted_fonts=converted_fonts)

템플릿 문자열을 직접 조립해 Template(result).render()로 실행하는 구조는 피한다.

10.2 출력 인코딩 적용

HTML에 출력되는 사용자 입력은 HTML 문맥에 맞게 이스케이프한다.

from markupsafe import escape

safe_value = escape(user_input)

10.3 허용 문자 기반 입력 검증

이름 변환 기능처럼 입력 형식이 명확한 경우 허용 문자 기반 검증이 효과적이다.

허용: 영문자, 숫자, 공백, 제한된 길이
차단: $, {, }, <, >, %, _, (, ), ., / 등 템플릿/객체 접근에 사용되는 문자

단, 입력 검증은 보조 방어책이며 템플릿 재렌더링 제거가 근본 대응이다.

10.4 템플릿 엔진 권한 제한

템플릿 엔진이 파일 시스템, OS 모듈, Python 내장 객체에 접근하지 못하도록 샌드박스 또는 제한된 렌더링 환경을 사용한다.

11. 학습한 점

  • SSTI는 XSS처럼 “화면에 입력이 보이는지”에서 시작하지만, 실제 실행 위치는 브라우저가 아니라 서버다.
  • 템플릿 엔진마다 문법이 다르므로 {{7*7}} 하나로 끝내지 않고 Jinja2, Mako, Twig, Smarty 문법을 구분해야 한다.
  • Spookifier는 Jinja2가 아니라 Mako 문법 ${...} 기반으로 접근해야 한다.
  • 문자열 포맷팅 후 템플릿으로 다시 렌더링하는 구조는 사용자 입력을 코드처럼 해석하게 만들 수 있다.
  • 보고서에서는 payload보다 “입력값이 템플릿 엔진에 도달하는 구조”를 설명하는 것이 중요하다.
